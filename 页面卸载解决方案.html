⚡ 项目卡点：页面卸载时数据丢失

所属项目：perf-monitor（前端性能监控 SDK）
涉及模块：unload.ts / queue.ts / sender.ts / storage.ts / index.ts
难度等级：⭐⭐⭐ 架构级
关键词：pagehide、visibilitychange、IndexedDB、异步竞态、浏览器生命周期

一、问题现象

BUG 用户关闭标签页后，队列中未发送的监控数据永久丢失。

表现：

  • 关闭页面后重新打开，IndexedDB 中无残留数据
  • 控制台无离线补发日志
  • 数据在页面关闭的瞬间静默丢失，无任何错误提示

二、根因分析

2.1 浏览器页面关闭的事件时序

visibilitychange → hidden（最先触发）
pagehide（紧随其后，几乎同时）
浏览器进程开始销毁，取消所有未完成的异步操作

2.2 旧设计的致命缺陷

旧设计中，pagehide 触发后走的是 完整的异步 sender 流程：

pagehide → queue.flush() → sender.send() [async] → fetch #1 → 失败，setTimeout 1s → fetch #2 → 失败，setTimeout 1s → fetch #3 → 失败 → saveToDB
核心矛盾 sender 的异步重试链需要 3+ 秒，但浏览器在 pagehide 后立即开始销毁进程。

setTimeout 回调被取消，fetch 被中断，saveToDB 永远执行不到。

2.3 为什么不是显而易见的？

  • 静默丢失：没有异常抛出，没有 console.error，数据悄悄消失
  • 本地开发不易复现：开发时服务端一直开着，sender 重试 0 次就成功，不会触发 saveToDB 路径
  • 正常 flush 场景没问题：页面存活时，异步重试有充足时间完成
  • Chrome DevTools 的误导：即使关闭标签页，DevTools 的 Network 面板仍可能显示 keepalive 请求，让人误以为"一切正常"

3.2 关键接口变化

模块 旧接口 新接口
queue.ts flush(): void — 清空队列并调用 sender 新增 drainQueue(): TransportItem[] — 取出快照并清空，不调 sender
unload.ts setupUnload(flush: () => void) — 单一回调，所有场景共用 setupUnload(normalFlush, urgentFlush) — 双回调，场景分流
index.ts setupUnload(flush) — 传 queue.flush setupUnload(flush, () => { drainQueue → saveToDB → sendBeacon })

四、实现细节 —— 逐文件逐行

4.1 queue.ts：新增 drainQueue()

// 文件：src/transport/queue.ts

/**
 * 取出队列中所有数据并清空，返回快照。
 * 与 flush() 的区别：不调用 sender，由调用方自行处理数据。
 * 专为 pagehide 场景设计 —— 此时不能依赖异步 sender。
 */
export function drainQueue(): TransportItem[] {
    if (queue.length === 0) return [];
    const snapshot: TransportItem[] = [...queue];  // 快照
    queue.length = 0;                               // 清空
    return snapshot;                                // 交给调用方
}
设计要点 与 flush() 共享同一个 queue 数组，避免数据重复或遗漏。两个函数的清空操作（queue.length = 0）谁先执行谁生效，后执行的发现队列为空直接 return。

4.2 unload.ts：双回调分流

// 文件：src/core/unload.ts

let normalFlushFn: (() => void) | null = null   // visibilitychange 用
let urgentFlushFn: (() => void) | null = null   // pagehide 用
let flushed = false                              // 防重复标记

export function setupUnload(
    normalFlush: () => void,   // 正常路径 → sender 异步重试
    urgentFlush: () => void,   // 紧急路径 → 同步写 DB + sendBeacon
): void {
    normalFlushFn = normalFlush
    urgentFlushFn = urgentFlush

    // visibilitychange：切 Tab → 走正常路径
    document.addEventListener('visibilitychange', () => {
        if (document.visibilityState === 'hidden') {
            doFlush()            // → normalFlushFn() (sender 异步)
        } else {
            flushed = false      // 页面恢复可见，重置防重复标记
        }
    })

    // pagehide：页面销毁 → 走快速通道，不经过 doFlush
    window.addEventListener('pagehide', () => {
        urgentFlushFn?.()         // → 直接写 DB + sendBeacon
    })
}

function doFlush() {
    if (flushed || !normalFlushFn) return
    flushed = true
    normalFlushFn()
}
关键决策 为什么 pagehide 不经过 doFlush()？因为 visibilitychange 与 pagehide 几乎同时触发，doFlush() 的 flushed 标记会导致 pagehide 的 flush 被静默跳过——这是一个之前修过的 Bug。

4.3 index.ts：构造快速通道

// 文件：src/index.ts（init 函数内）

setupQueue(config);
const send = createSender(config);
onFlush(send);

// ── 双路径注入 ──
setupUnload(
    // 路径1：正常路径（visibilitychange）
    flush,   // → queue.flush() → sender.send() [async + 重试]

    // 路径2：紧急路径（pagehide）
    () => {
        const snapshot = drainQueue();     // ① 同步取出并清空队列
        if (snapshot.length === 0 || !config) return;

        saveToDB(snapshot).catch(() => {}); // ② 立即写 IndexedDB（异步但尽快）

        const body = JSON.stringify(snapshot);
        navigator.sendBeacon?.(config.url, body); // ③ 最后尝试发送
    }
);
设计要点 saveToDB 虽然是异步的，但在 pagehide 中浏览器通常会允许 IndexedDB 事务完成。sendBeacon 是浏览器级别的 fire-and-forget，即使页面关闭也会在后台完成。双保险：DB 确保持久化，sendBeacon 尝试即时发送。

五、问题发现与定位过程

5.1 测试场景设计

模拟断网 → 制造数据 → 关闭页面 → 重新打开 → 检查 IndexedDB
  1. 启动 Express 服务端（端口 3001）
  2. 打开测试页面（http://localhost:3001）
  3. Ctrl+C 停掉服务端（模拟断网）
  4. 点击按钮触发数据采集（LCP / FID / JS错误等）
  5. 数据进入队列，sender 尝试发送但服务端不在 → 触发重试
  6. 直接关闭标签页，不等重试完成
  7. 重新打开页面，检查 IndexedDB 和 Console

5.2 定位手法

步骤方法结论
① 验证 IndexedDB 本身 在 Console 手动执行 indexedDB.open + add ✅ IndexedDB 读写正常，排除存储层问题
② 验证断网时 sender 行为 停服务端，触发数据，观察 Console 重试日志 ✅ sender 重试 3 次后调用了 saveToDB，但仅在页面存活时
③ 缩小范围 页面存活时断网 → 数据能写 DB；关闭页面时 → 数据丢失 ⚠️ 问题锁定在"关闭页面"这个动作上
④ 追踪 pagehide 链路 在 unload.ts / queue.ts / sender.ts 加 console.log 逐级追踪 ❌ pagehide → flush → sender.send 被调用，但 saveToDB 从未执行
⑤ 确认根因 分析 sender 异步重试时间线 vs 浏览器销毁时间线 ❌ sender 的 setTimeout 回调在页面销毁时被取消

5.3 关键调试技巧

// 在 pagehide 中加日志，但注意 console.log 也可能来不及
// 改用 navigator.sendBeacon 发一条最小调试数据：
window.addEventListener('pagehide', () => {
    navigator.sendBeacon('/debug', JSON.stringify({
        event: 'pagehide',
        queueLength: queue.length,         // ← 关键：此时队列还有数据吗？
        timestamp: Date.now()
    }));
});

六、技术深度总结

6.1 涉及的核心概念

🔹 浏览器页面生命周期 visibilitychange vs pagehide 的触发时机和顺序
🔹 异步竞态条件 setTimeout / Promise 在页面销毁时被取消的机制
🔹 keepalive 的局限性 fetch keepalive 只保请求，不保重试链
🔹 IndexedDB 事务生命周期 pagehide 中 IndexedDB 事务的特殊待遇
🔹 sendBeacon 的设计意图 为什么 W3C 专门设计了 sendBeacon——就是为了这个场景
🔹 双路径架构 同一种"发送"操作，不同场景走不同策略

6.2 面试可展开的讨论点

  • 为什么不在 pagehide 中用同步 XMLHttpRequest？—— 已废弃，浏览器会忽略
  • sendBeacon 有 64KB 限制，超了怎么办？—— 分批发送或只用 IndexedDB 持久化
  • 如果 IndexedDB 在 pagehide 中也写不进去呢？—— 这就是终极兜底：sessionStorage 存 JSON，下次 init 时检测
  • 多个 Tab 同时关闭时，IndexedDB 事务会冲突吗？—— IndexedDB 支持多连接，readwrite 事务会排队
